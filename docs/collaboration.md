# 自动化测试协作规范

## 1. 角色与职责

### 测试负责人

- 维护测试框架、fixture、页面对象和 core 能力。
- 审查新增测试是否稳定、可清理、可观测。
- 管理 known_flaky 的 owner 和期限。
- 查看失败聚类与趋势。

### 用例作者

- 编写最小行为型用例。
- 使用动态数据并清理。
- 不复制鉴权、请求、定位和等待逻辑。
- 为失败提供清晰断言和上下文。

### 值班人员

- 判断失败属于环境、产品、配置还是框架。
- 保留 trace_id、日志和报告证据。
- 不在未确认原因时反复重跑。
- 按影响范围和 owner 升级。

### 产品与开发负责人

- 确认产品预期。
- 处理产品断言失败和接口契约变化。
- 确认 known_flaky 对应修复计划。

## 2. 分支与提交

建议流程：

```text
master
→ feature/fix 分支
→ 本地专项测试
→ Pull Request
→ CI
→ Review
→ 合并 master
```

提交信息应说明：

- 新增能力。
- 修复内容。
- 测试结果。
- 风险或兼容性变化。

不得把报告、截图、数据库、token、cookie 或 `.env` 提交到仓库。

## 3. 新增测试的最低要求

每个新增测试必须明确：

- 测试什么用户行为或业务契约。
- 使用哪个环境档位。
- 是否并行。
- 使用哪些动态数据。
- 如何清理数据。
- 失败时能看到什么上下文。
- 是否有稳定定位或稳定接口。

测试命名应描述行为：

```python
def test_order_can_be_created_and_searched() -> None:
    ...
```

不应使用：

```python
def test_case_1() -> None:
    ...
```

## 4. 分层边界

- 测试用例负责业务步骤和断言。
- `services/` 负责业务 API 操作。
- `core/` 负责请求、日志、trace、限流、熔断和底层能力。
- `pages/` 负责 UI 定位和页面操作。
- `utils/` 负责数据生成。
- `testdata/` 负责静态数据和 schema。

用例中不得：

- 直接写 `httpx.Client` 请求。
- 直接重复登录逻辑。
- 直接散落 CSS/XPath。
- 使用固定 `sleep` 等待页面。

## 5. Pull Request 检查清单

- [ ] 测试只聚焦一个清晰行为。
- [ ] 使用动态测试数据或合法静态数据。
- [ ] 数据清理可证明。
- [ ] 没有裸 HTTP 请求。
- [ ] UI locator 位于 page object。
- [ ] 等待使用 Playwright 显式断言。
- [ ] 失败可看到 trace_id、请求响应或截图。
- [ ] 新依赖已更新 `pyproject.toml` 与 `uv.lock`。
- [ ] `ruff check .` 通过。
- [ ] 本地专项和完整回归通过。
- [ ] Docker 三通道通过。
- [ ] 文档和项目记忆已同步。

## 6. 失败处理和升级

### 环境问题

由值班人员先确认：

- app 健康检查
- DNS、代理、网络
- Docker 日志
- 熔断状态

恢复后再重试。

### 产品断言失败

提供证据：

- 测试 nodeid
- trace_id
- 请求和响应
- JSON Schema 差异
- 页面截图
- 复现步骤

测试负责人和开发共同确认产品预期。

### 框架问题

由测试负责人或提交作者处理：

- fixture
- 页面对象
- 客户端封装
- 配置接线
- 测试数据生成

### 未知问题

不允许直接关闭或无限重试。

先记录，再由测试负责人归类。

## 7. known_flaky 治理

只有确认属于：

- 产品异步行为。
- 已知竞态。
- 暂无法消除的外部依赖波动。

才允许登记 `known_flaky`。

建议默认期限：

```text
14 天
```

到期前必须：

- 修复。
- 删除用例或重写。
- 更新 issue 和期限。

不允许：

- 只写 `flaky` 不写业务原因。
- 无 owner。
- 无 issue。
- 无过期时间。
- 把网络故障长期隐藏为 known_flaky。

## 8. 报告协作

### 常规结果

优先查看：

- GitHub Actions Job Summary
- GitHub Pages Allure
- analytics `summary.md`

### 失败证据

必须保留：

- Actions run 链接
- artifact
- trace_id
- 失败分类
- 相关日志
- 页面截图

### 趋势审查

发现以下情况时升级：

- flaky 连续上升。
- 同一模块失败增加。
- 某类别集中出现。
- E2E 连续重试。
- 报告缺失或生成失败。

## 9. Secret 与环境变量

- 密码、token、webhook 只放 GitHub Secrets 或环境变量。
- 不打印 token、Cookie、Authorization。
- 请求附件必须继续脱敏。
- 生产只读身份与预发账号分离。
- 更换 secret 后要验证 CI 和生产巡检。

## 10. 生产变更协作

生产自动化能力上线前必须共同确认：

- 测试负责人：测试范围和只读保证。
- 后端负责人：接口稳定和限流阈值。
- 运维负责人：网络、证书、告警和权限。
- 产品负责人：巡检指标和告警解释。

生产巡检不得包含：

- 注册
- 登录创建 session
- 订单新增
- 订单修改
- 订单删除
- 数据库清理

## 11. 完成定义

一项自动化工作完成必须同时满足：

- 用例稳定通过。
- 失败可诊断。
- 数据可清理。
- 报告可查看。
- 依赖可复现。
- CI 可执行。
- 文档和记忆已更新。
- 没有新增未治理 flaky。

## 12. 沟通模板

```text
失败用例：
运行环境：
CI Run：
trace_id：
失败分类：
首次失败时间：
复现次数：
现象：
请求/响应或截图：
判断：
下一步 owner：
预计处理时间：
```

沟通时先给证据，再给判断；不要把“重跑后通过”当作结论。
