# 自动化测试框架学习路径（详细版）

## 文档用途

本文件是从零搭建一个面向线上产品的 UI/API 自动化测试框架的七阶段学习路线，是 AI 分阶段教学的唯一事实来源。AI 每次生成教学内容前，必须先阅读本文件与 `docs/project-memory.md`，确认当前阶段与进度，不得自行发挥或跳步。

被测系统为本地部署的“订单管理系统”（`app/`），提供注册、登录、鉴权、订单增删改查、分页搜索，以及明确的成功与失败场景。自动化框架代码放在 `automation/`，与被测系统互不耦合。

## 使用规则

1. 严格按阶段推进，上一阶段验收未通过，不得进入下一阶段。
2. 每节课完成后，必须同步更新 `docs/project-memory.md`。
3. 本文件只定义“做什么、学什么、完成后具备什么功能、如何验收”；每一节课的逐步操作步骤与完整代码由 AI 在进入对应阶段后，结合项目实际代码生成。
4. 若学习路径与项目实际代码不一致，以实际代码为准，并先修正本文件与记忆文件。

## 阶段 0：项目准备与被测系统搭建（前置阶段）

### 阶段目标

建立学习项目骨架，交付一个本地可部署的前后端被测系统，并生成教学文档，为阶段一开始扫清障碍。

### 具体内容

1. 在指定目录创建学习项目根目录，规划 `app/`（被测系统）、`automation/`（自动化框架）、`docs/`（教学文档）三块边界。
2. 实现后端：FastAPI + SQLite，提供注册、登录、鉴权，以及订单的增删改查、分页与搜索；提供明确的参数校验、未授权、资源不存在等失败场景；自动生成 OpenAPI 文档（`/docs`）。
3. 实现前端：登录/注册页、订单列表页、新增与编辑表单，元素使用稳定的 `data-testid` 属性，前端由后端直接托管，无需 npm 构建。
4. 提供启动脚本与部署说明，一条命令启动前后端。
5. 初始化 git 仓库、`.gitignore`，创建学习路径与项目记忆文档。

### 学习内容

- 一个最小可用的前后端系统如何组织。
- REST API 的资源、方法、状态码与错误响应设计。
- 前端与后端的交互方式。
- 可测试性设计：接口稳定、元素定位稳定、多环境可配置。

### 完成后具备的功能

- 本地可启动完整系统，浏览器中能注册、登录并完成订单增删改查。
- 能通过接口文档或命令行调用后端 API。
- 项目结构清晰，框架代码与被测系统代码互不耦合。

### 验收标准

- 启动脚本执行成功，前端页面与后端接口均可访问。
- 通过浏览器完成一次注册、登录、新增、查询、修改、删除的完整流程。
- 通过接口文档或 curl 调通核心接口。
- git 仓库已初始化，`.gitignore` 生效。

## 阶段一：环境与工具链地基

### 阶段目标

建立 Python 工程化环境，跑通第一个 pytest 用例并产出报告，掌握 pytest 的核心机制。

### 具体内容

1. 使用 uv 或 Poetry 初始化 `automation/` 的 Python 环境，生成并锁定依赖。
2. 安装 pytest，规划基础目录：`automation/tests/`、`automation/config/`、`automation/core/`、`automation/conftest.py`、`automation/pytest.ini`。
3. 编写 3 至 5 个基础用例，练习用例命名与 `assert` 断言。
4. 练习 fixture 的创建、`scope`（function/session）生命周期差异，以及 `conftest.py` 共享 fixture。
5. 使用 `@pytest.mark.parametrize` 参数化。
6. 定义自定义 markers 并在 `pytest.ini` 注册，练习 `-m` 筛选。
7. 熟悉 `pytest -v`、`-k`、`-m`、`--maxfail`。
8. 接入一个最简 HTML 报告。
9. 提交代码，确认依赖锁文件生效。

### 学习内容

- pytest 的用例发现、命名规则与断言失败信息。
- fixture 的依赖注入、作用域、setup/teardown。
- `conftest.py` 的作用范围。
- 参数化与标记的组织方式。
- 虚拟环境与依赖锁定的意义。

### 完成后具备的功能

- 项目可被 pytest 统一执行，具备基础用例、共享 fixture、参数化、标记与 HTML 报告。

### 验收标准

- 全部用例通过。
- `-k` 与 `-m` 能正确筛选。
- 能观察到 function 与 session 两种 fixture 的生命周期差异。
- HTML 报告生成成功。
- 依赖锁文件已提交。

## 阶段二：API 自动化最小闭环

### 阶段目标

针对订单管理系统的鉴权与订单模块，建立“core 底层封装 + service 业务封装 + 用例断言”三层结构。

### 具体内容

1. 实现 `core/api_client.py`：统一封装 httpx 或 requests，收口 base_url、默认请求头、超时、统一异常与请求响应日志。
2. 实现 `core/logger.py` 与 `core/exceptions.py`。
3. 实现 `services/auth_service.py`：注册、登录、获取 token。
4. 实现 `services/order_service.py`：订单新增、查询、列表、修改、删除。
5. 编写 `tests/api/test_auth.py` 与 `tests/api/test_order.py`，覆盖成功与失败场景。
6. 在 `conftest.py` 提供会话级 base_url fixture 与登录后的 token fixture。
7. 练习状态码、响应体字段、错误码与错误信息断言。

### 学习内容

- httpx/requests 的请求与响应处理。
- 鉴权与 token 的获取、传递。
- HTTP 状态码与业务错误的区分。
- 日志、异常与分层的设计动机。

### 完成后具备的功能

- 一个模块的 API 用例可独立运行，用例只描述业务步骤，底层细节进 core 与 service。

### 验收标准

- 全部 API 用例通过。
- 用例中不出现裸 HTTP 调用，鉴权逻辑不重复。
- 人为制造一次失败，日志中能看到完整请求与响应。
- 新增一条同模块用例，无需复制鉴权和基础配置代码。

## 阶段三：数据驱动、配置与报告

### 阶段目标

把硬编码数据抽离，引入多环境配置与结构化报告。

### 具体内容

1. 实现 `config/settings.py`：使用 pydantic-settings 读取 yaml 并做类型校验。
2. 创建 `config/dev.yaml`、`config/staging.yaml`。
3. 在 `conftest.py` 用 `pytest_addoption` 增加 `--env` 参数。
4. 创建 `testdata/*.yaml`，用 `parametrize` 驱动用例。
5. 接入 Allure：`@allure.step` 与请求响应 attachment。
6. 配置失败用例自动附带请求响应上下文。

### 学习内容

- yaml 数据组织。
- pydantic-settings 配置读取与校验。
- pytest 命令行参数扩展。
- Allure 的 step、attachment 与报告阅读。

### 完成后具备的功能

- 同一套用例可跑多组数据，切环境只改参数，失败可通过报告定位。

### 验收标准

- `--env=dev` 与 `--env=staging` 切换后配置正确生效。
- 数据驱动跑通多组数据。
- `allure serve` 能展示 step 与附件。
- 配置缺失或类型错误时给出明确报错。

## 阶段四：UI 自动化与页面对象

### 阶段目标

引入 Playwright 或 Selenium，用页面对象模型封装订单系统页面，UI 用例本地稳定运行并支持失败截图。

### 具体内容

1. 安装浏览器自动化工具与驱动。
2. 实现 `core/web_driver.py`，在 fixture 中管理浏览器生命周期。
3. 实现 `pages/base_page.py`：点击、输入、显式等待、截图。
4. 实现 `pages/login_page.py` 与 `pages/order_page.py`。
5. 编写 `tests/ui/test_login_ui.py` 与 `tests/ui/test_order_ui.py`。
6. 优先使用 `data-testid` 定位，显式等待替代固定 sleep。
7. 通过 hook 实现失败自动截图。

### 学习内容

- DOM 与 CSS/XPath 选择器。
- 显式等待与隐式等待的区别。
- 页面对象模型。
- 浏览器生命周期与失败留痕。

### 完成后具备的功能

- UI 用例本地稳定运行，定位不依赖脆弱路径，失败自动截图。

### 验收标准

- UI 用例连续多次执行无随机失败。
- 定位集中在页面对象内。
- 人为制造失败能自动截图。
- 浏览器在用例结束后正确关闭。

## 阶段五：稳定性、并发与 CI/CD 接入

### 阶段目标

加入分组、并行、重试能力，接入持续集成，实现提交后自动执行与报告归档。

### 具体内容

1. 定义 `smoke`、`regression` 等 markers。
2. 引入 pytest-xdist 并行执行 API 用例。
3. 实现 UI 并行策略，关键用例标记 `serial`。
4. 引入 pytest-rerunfailures，只重试网络/环境类失败。
5. 编写 Dockerfile 与 docker-compose，一键复现环境。
6. 创建 CI 流水线：检出、安装依赖、启动被测系统、执行 API 与 UI、归档报告、发送通知。

### 学习内容

- pytest-xdist 并行模型。
- UI 并行与串行标记。
- 失败重试的适用场景。
- CI 的 job、artifact、secret。
- Docker 容器化执行环境。

### 完成后具备的功能

- 流水线自动运行、失败可阻断或告警、报告有历史趋势、环境可复现。

### 验收标准

- docker compose 一键复现环境。
- CI 在提交后成功触发并跑通用例。
- 报告归档且可查看历史趋势。
- 失败时通知带报告链接。

## 阶段六：测试数据、鉴权、契约与混合场景

### 阶段目标

建设测试数据生命周期、鉴权管理与契约校验，打通 UI 与 API 的端到端旅程。

### 具体内容

1. 实现 `utils/data_generator.py`：Faker 动态造数。
2. 通过 fixture 做数据准备与 teardown 清理。
3. 实现 `core/db_client.py`：数据库校验与清理。
4. 处理 token 获取、缓存与刷新。
5. 创建 `testdata/schemas/*.json`，用 jsonschema 做响应结构契约断言。
6. 学习 mock/stub 隔离外部依赖。
7. 编写 `tests/e2e/test_user_journey.py`：UI 造数 + API 校验 + UI 验证。

### 学习内容

- 测试数据生命周期。
- 数据库读写校验。
- OAuth/token 与 session 管理。
- JSON Schema 契约校验。
- mock/stub 适用场景。

### 完成后具备的功能

- 用例不依赖手写死数据，数据自动准备与清理，契约变更可捕获，关键旅程端到端跑通。

### 验收标准

- 端到端用例稳定通过。
- 用例结束后无残留数据。
- 修改响应字段能被 JSON Schema 捕获。
- token 过期能自动刷新或明确报错。

## 阶段七：线上化加固与运营

### 阶段目标

面向预发与线上环境设计风险受控的运行策略，建立稳定性治理与运营文档。

### 具体内容

1. 环境分级：线上只跑冒烟巡检，预发跑回归，本地跑全量。
2. 实现流量染色、只读开关、限流与熔断。
3. 为请求贯穿 trace_id，关联日志。
4. 建立 flaky 用例管理，区分产品缺陷与框架不稳定。
5. 建立失败聚类与报告趋势监控。
6. 沉淀运行手册与协作规范。

### 学习内容

- 线上环境风险控制。
- trace_id 与日志关联。
- 稳定性治理。
- 框架长期维护规范。

### 完成后具备的功能

- 预发稳定高频运行，线上受控执行最小巡检集，问题可快速定位。

### 验收标准

- 预发连续高频运行稳定。
- 线上巡检集最小且受控。
- 日志可追溯。
- 运行手册完整。
